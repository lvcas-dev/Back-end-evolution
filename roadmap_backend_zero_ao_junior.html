Fase 1 Alfabetização digital e lógica ~200h · Dificuldade: 7/10 ▼

Idêntica para qualquer trilha. Backend não muda a necessidade de entender como a máquina pensa — muda apenas o que você vai construir depois.

Conteúdo obrigatório
Como o computador funciona
CPU, memória, SO, processos, threads. O que acontece quando você executa um programa.
Lógica de programação
Variáveis, tipos, condicionais, loops, funções. Pseudocódigo antes de qualquer sintaxe.
Estruturas de dados
Array, lista, pilha, fila, dicionário/mapa. Complexidade O(n) — você precisa saber isso em entrevista.
Algoritmos fundamentais
Busca linear e binária, ordenação básica. Recursão com exemplos concretos.
Python como veículo
Python é a linguagem de entrada ideal para backend: sintaxe limpa, vasta adoção em APIs e dados.

AtividadeHoras/semanaExemplo concreto

Código prático12hImplementar do zero o que aprendeu
Técnica Feynman1hExplicar em papel para um leigo imaginário
Técnica Feynman: após estudar recursão ou complexidade, feche tudo e tente explicar em voz alta. Onde você gaguejar é onde ainda não sabe. Volte exatamente para aquele ponto.
Marco obrigatório — Milestone 1
Jogo da forca ou calculadora de RPN no terminal
Sem tutorial. Você planeja no papel, lê a documentação, escreve o código. Critério: roda sem erros e você consegue explicar cada linha sem consultar nada.
Recursos
Livro: "Pense em Python" — gratuito em PT-BR, direto ao ponto
Curso: CS50 (cs50.harvard.edu) — gratuito, cobre hardware + lógica + algoritmos com rigor
Prática: HackerRank trilha Python — exercícios progressivos com feedback automático
Fase 2 Ecossistema de desenvolvimento ~120h · Dificuldade: 5/10 ▶

Backend vive no terminal. Quem não sabe operar linha de comando com fluência não consegue depurar servidores, gerenciar processos nem fazer deploy.

Conteúdo obrigatório
Terminal / Linux
Navegação, permissões, pipes, variáveis de ambiente, processos. Aprenda em Linux, não em Windows.
Git e GitHub
init, add, commit, push, pull, branch, merge, rebase básico. Resolver conflitos sem GUI.
SQL sólido
SELECT, INSERT, UPDATE, DELETE, JOIN (inner/left/right), subqueries, índices, transações. PostgreSQL.
Como ler documentação
Estrutura de uma doc oficial. Diferença entre referência de API e guia de uso. Leia docs, não tutoriais.
Redes básicas
HTTP, HTTPS, DNS, TCP/IP em nível conceitual. O que acontece quando você acessa uma URL.
Marco obrigatório — Milestone 2
Sistema de cadastro no terminal com PostgreSQL
Script Python que conecta num banco PostgreSQL local, faz CRUD completo via linha de comando. Histórico versionado no Git com mensagens de commit descritivas. Critério: outro dev clona, lê o README e reproduz tudo sem precisar te perguntar nada.
Recursos
Terminal: linuxcommand.org — gratuito, cobre o essencial em 2 semanas
Git: git-scm.com/doc — seção "Pro Git" gratuita e completa
SQL: postgresql.org/docs — documentação oficial do PostgreSQL
Redes: "HTTP: The Definitive Guide" caps. 1–4 — base sólida para entender o protocolo que você vai servir
Fase 3 Especialização — backend com Python ~300h · Dificuldade: 7/10 ▶

A trilha abaixo é sequencial e não pode ser reordenada. Cada bloco pressupõe o anterior. FastAPI foi escolhido por ser moderno, próximo de como o mercado escreve código em 2025 e com documentação excelente.

Critério: URL pública rodando (Railway ou Render, ambos gratuitos), código no GitHub com README explicando as decisões de arquitetura — não apenas como instalar.

Fase 4 Portfólio e habilidades técnicas profissionais ~100h · Dificuldade: 4/10 técnico, 8/10 disciplina ▶

A diferença entre um candidato que passa na triagem técnica e um que não passa raramente é conhecimento — é capacidade de depurar ao vivo e explicar o que fez.

Habilidades de depuração
Leitura de logs
Stack traces Python, logs de servidor, identificar a linha exata do erro antes de buscar no Google.
Depurador (pdb/debugpy)
Breakpoints, inspecionar variáveis em runtime, step over/into. Não apenas print().
Diagnóstico de API
Postman ou curl para isolar se o problema é no cliente ou no servidor. Headers, body, status codes.
Problemas de banco
EXPLAIN em queries lentas, índices faltando, deadlocks. Saber identificar N+1 queries.

Marco obrigatório — Milestone 4 (portfólio mínimo viável)
3 projetos deployed + apresentação técnica gravada
Milestone 2 refatorado com ORM e Git. Milestone 3 (API completa). Mais 1 projeto novo integrando um serviço externo real (envio de e-mail, pagamento sandbox, armazenamento de arquivos). Critério de saída: você grava um vídeo de 5 minutos explicando as decisões técnicas de cada projeto — banco escolhido, estrutura de autenticação, por que usou cada biblioteca. Se travar na explicação, não está pronto para entrevista técnica.
Recursos
Depuração: "Rubber Duck Debugging" — explique o problema em voz alta passo a passo antes de pedir ajuda a alguém
README: github.com/readme — guia oficial com exemplos de bons READMEs
SQL performance: use-the-index-luke.com — guia gratuito sobre índices e otimização de queries
Armadilhas O que NÃO fazer — específico para backend Leia antes de começar ▶
✕
Aprender Django antes de entender HTTP: Django abstrai demais para quem não sabe o que está por baixo. Você vai seguir tutoriais sem entender o que o framework está fazendo por você. FastAPI expõe mais o mecanismo.
✕
Pular Docker achando que é avançado: todo processo seletivo de estágio backend em 2025 vai perguntar sobre containers. Não é avançado — é o mínimo esperado.
✕
Usar ORM sem ter aprendido SQL puro primeiro: quando o ORM gerar uma query lenta (e vai gerar), você não vai saber diagnosticar se não souber SQL. A ordem importa.
✕
Guardar senha em texto puro "só para testar": hábitos ruins de segurança aparecem nos projetos do portfólio. Recrutador técnico vai olhar seu código.
✕
Fazer deploy sem variáveis de ambiente: chave de API ou senha de banco no código commitado é eliminatório em qualquer empresa séria.
✕
Não escrever nenhum teste: "vou adicionar testes depois" é sinônimo de nunca. Escreva testes enquanto desenvolve, mesmo que básicos.
✕
Aprender Node.js/Go/Rust antes de dominar Python: a linguagem importa menos do que os conceitos. Domine uma stack completamente antes de diversificar.
✕
Ignorar mensagens de erro: todo erro tem uma causa raiz legível. Quem copia o erro direto no Google sem ler o stack trace não está aprendendo a depurar.
